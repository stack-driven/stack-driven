# Stack-Driven Spec Authority Model

This directory defines the repository-level authority model for Stack-Driven specifications. It is separate from `product-guidelines/`, which remains the generated, per-product output directory.

## Authority files

- `specs/manifest.yaml` is the canonical registry of Stack-Driven specs, sessions, dependencies, output paths, context paths, optionality, lifecycle status, and loading hints.
- `specs/index.md` is the human-readable overview of the registry and dependency graph.
- `specs/migration-note.md` explains how the new authority model relates to existing `product-guidelines/` outputs.

## Core principles

1. User journey is the root dependency for product-facing specs.
2. The manifest describes expected framework artifacts; generated product outputs are still product-specific.
3. Review status is separate from lifecycle status so AI drafts cannot be mistaken for human-reviewed specs.
4. `.ctx.md` files are loading optimizations, not independent sources of authority.
5. Optional and conditional specs must have explicit skip/defer guidance.
6. No runtime dependency is required to use this model in Phase I.

## Manifest schema

Each entry under `specs:` follows this shape:

| Field | Required | Purpose |
|---|---:|---|
| `id` | yes | Stable machine-readable identifier. Use dotted names such as `journey.user`. |
| `title` | yes | Human-readable spec name. |
| `session` | yes | Cascade session or extension identifier. |
| `command` | yes | Slash command that produces or manages the spec. |
| `group` | yes | Broad registry group: `core`, `phase`, `post_core`, or `delivery`. |
| `kind` | yes | Artifact type, such as `product_spec`, `phase_spec`, `execution_record`, or `scaffold`. |
| `purpose` | yes | Why the spec exists and what decision/value it controls. |
| `required_mode` | yes | `required`, `recommended`, `conditional`, `optional`, or `support`. |
| `condition` | yes | Trigger for conditional/optional specs, otherwise `null`. |
| `lifecycle` | yes | Spec-definition status. See lifecycle values below. |
| `default_review_status` | yes | Initial trust level for generated outputs. |
| `dependencies.required` | yes | Spec IDs that must exist first. |
| `dependencies.optional` | yes | Spec IDs used when present. |
| `root_dependency` | yes | `true` only for the user journey root. |
| `outputs.paths` | yes | Full generated output path(s), usually under `product-guidelines/`. |
| `outputs.ctx_paths` | yes | Condensed `.ctx.md` path(s), or an empty list when none exists. |
| `skip_policy` | yes | Whether the spec may be skipped/deferred and how to revisit. |
| `relevance` | yes | Loading hints for agents and future Phase II automation. |

## Lifecycle values

Lifecycle describes the spec definition in the Stack-Driven framework, not whether a specific product has generated the output.

- `active`: current and supported by the cascade.
- `deferred`: intentionally delayed; revisit guidance must be present.
- `skipped`: intentionally omitted for a product or flow; skip reason and revisit guidance must be present.
- `superseded`: replaced by a newer spec ID or output.
- `deprecated`: retained for compatibility but should not be used for new work.

## Review status values

Review status describes trust and authority of a concrete spec artifact.

- `ai_drafted`: generated by an AI workflow and not yet approved by a human.
- `human_reviewed`: explicitly reviewed and accepted by a human.
- `authoritative`: human-reviewed and designated as the controlling source for conflicts.

Generated `product-guidelines/` outputs default to `ai_drafted` unless the manifest or artifact metadata says otherwise.

## Required mode values

- `required`: normal core-cascade output.
- `recommended`: strongly encouraged, but a product may proceed with documented rationale.
- `conditional`: required only when the condition is true.
- `optional`: post-core extension or specialized deep-dive.
- `support`: intermediate or implementation-support artifact that feeds an authoritative output.

## Skip and defer model

If `skip_policy.allowed` is `true`, a product-specific run may skip or defer the spec only when it records:

- `skip_reason`: why the spec is not being generated now.
- `revisit_when`: condition that should trigger reconsideration.
- `revisit_owner`: optional owner or role responsible for revisiting.

Required specs set `skip_policy.allowed: false`. Missing required outputs indicate an incomplete cascade, not a skipped spec.

## Conflict hierarchy

When sources disagree, resolve conflicts in this order:

1. Human-reviewed or authoritative spec listed in `specs/manifest.yaml`.
2. Approved issue plan or reviewed ADR that explicitly amends a spec.
3. Implementation detail in code or command files.
4. AI-drafted generated output.
5. Templates, examples, or informal notes.

Stale implementation does not override a reviewed spec. It indicates either a migration task or a bug.

## `.ctx.md` authority rule

A `.ctx.md` file is a condensed loading artifact. Use it when the manifest says `prefer_ctx: true`, but treat the corresponding full `.md` output as the human-readable source. If a `.ctx.md` file conflicts with its full `.md`, regenerate or correct the context file rather than treating it as authoritative.
